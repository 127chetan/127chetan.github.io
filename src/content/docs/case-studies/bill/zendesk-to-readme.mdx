## Context

In 2021, `developer.bill.com` was a Zendesk help site template. This help site was under-maintained, unstructured, and built for an API product that was never designed for external API developers.

<CardGrid>
  <Card title="Docs organization issues">
    Guides & API reference lived on the same page. No separation by audience, skill level, or use case.
  </Card>
  <Card title="Missing business cases">
    Standard cases were documented. Detailed usage examples, edge cases, & realistic integration scenarios were absent.
  </Card>
</CardGrid>

#### The underlying API compounded the problem

The BILL v2 API was built by BILL engineering for BILL engineering. When leadership chose to make the API public, BILL v2 would have benefited from a customer-centric API design strategy.

Failure responses returned HTTP 200. Each operation (GET, PUT, PATCH, DELETE) was a POST request. Response field names were unhelpful, and many responses ignored values set in the request.

#### The brief
- Build an API developer audience. Cater to all skill levels.
- Use modern tooling integrating docs with engineering workflows.
- Focus on driving integration partnerships. Integrations result in direct revenue.
- Build an experience that positions BILL as a modern company that offers API products.

## The vendor approval battle

The brief called for a SaaS platform that integrated with engineering workflows. I knew that ReadMe was a great fit. I built and maintained `docs.clover.com` on ReadMe at Clover Network from 2017 to 2021.

I considered 2 alternatives against a set of features (in the table below). These features fit the brief and were critical for a technical writing team of one.

| Feature | ReadMe | Confluence | Kong (in 2021) |
|---|---|---|---|
| SaaS setup | ✓ | ✗ | ✗ |
| Dedicated API docs suite | ✓ | ✗ | ✗ |
| Automated OpenAPI sync | ✓ | ✗ | ✓ |
| Interactive live endpoint testing | ✓ | ✗ | ✓ |
| Built-in docs CMS & changelog editor | ✓ | ✓ | ✗ |

Getting ReadMe approved as a BILL vendor faced internal resistance. Bringing in a smaller-scale vendor for a BILL-branded website triggered scrutiny across the procurement and information security teams.

I did not want to wait for approval before building documentation. Between November 2021 and January 2022, I built the real docs in a personal ReadMe project. In parallel, I started writing the BILL v2 API OpenAPI spec.

My prior relationship with the ReadMe team from my years at Clover Network meant they understood the situation. They extended my trial repeatedly across those months, keeping the project alive while approval was pending.

For vendor approval, I drew on my track record with `docs.clover.com` and worked directly with the ReadMe team to produce all internal documentation required for BILL's vendor review. ReadMe participated in internal reviews. In January 2022, ReadMe was approved.

## Information architecture foundation

In January 2022, `developer.bill.com` was published as a ReadMe project. The website included 4 core sections for documentation.

| Section | Primary audience | Development stage | Purpose |
|---|---|---|---|
| Guides | Business decision makers; Developers | Early development & testing | Conceptual introductions, working examples, & tutorials by business case. Explains the *why* and *how* without requiring the spec. |
| API Reference | Developers | Maturing integration; specific configuration requirements | Published OpenAPI spec with field-level docs, endpoint descriptions, & a live sandbox for making API requests directly in the docs. |
| Recipes | Developers | Maturing integration; specific configuration requirements | Python scripts demonstrating endpoint orchestration for common integration workflows. |
| Release Notes | Business decision makers; Developers | - | Released features, changes, & required developer actions before a change can affect live integrations. |

One security constraint shaped the entire site: every interactive element points to the BILL sandbox environment. Production URLs appear in the Guides section for reference, but there is no way to execute calls to production from the website. This was a deliberate infosec decision to prevent the docs site from becoming a surface for production attacks.

## Outcome

The site launched with a modern look and feel. Internal BILL stakeholders were satisfied with the outcome. BILL engineers adopted it for sandbox testing — a practical endorsement from the team closest to the API.

Infosec began using the site to simulate DOS attacks against the sandbox. That wasn't planned. It was a signal that the site had become genuinely useful infrastructure inside the company.

The developer response was qualitatively positive across the board. API customers said it made BILL feel like a modern company. Documentation feedback was consistently green. Issues with v2's API design were real and ongoing — but developers were clear that the problem was the API, not the docs.

The most telling outcome: the most common developer support question — *how do I log in to the API?* — disappeared within weeks of launch. Developers were finding the answer on their own, getting authenticated, and moving on to their actual integration work.
