## Context

In 2021-2022, the BILL v2 API had no OpenAPI spec. Without a spec, BILL couldn't leverage what OpenAPI enables: human and machine readability, a single source of truth, SDK generation, mock servers, and automated testing.

To publish an OpenAPI spec as API reference documentation on ReadMe, the requirement was a complete OpenAPI spec. Without engineering resources for help, my action plan was to write the spec from scratch.

OpenAPI spec for 340+ endpoints. Solo. In 3 months!

## Tooling challenges in 2022

My first complete draft of the BILL v2 API OpenAPI spec was ~178,000 lines. Writing a YAML file at that scale is not just a documentation problem. It is an engineering problem! A single incorrect indentation in a 1000-line YAML block is nearly impossible to debug by eye.

At the time, I built a toolchain to catch errors in real time.

<CardGrid>
  <Card title="Live lint with Stoplight.io">
    `stoplight.io` caught spec violations at the line level. I knew instantly if any update would pass validation.
  </Card>
  <Card title="Render with Swagger Editor">
    `editor.swagger.io` rendered the spec as structured output each time I completed docs for an endpoint.
  </Card>
</CardGrid>

:::tip[The split decision]
Even with live linting, maintaining a single 178,000-line spec file would eventually become unmanageable. Halfway through the effort, my powerful work machine was struggling to respond.

I made the decision early to split the spec into smaller files organized by BILL's core workflows.
:::

## Direction: 10 OpenAPI spec files

The final OpenAPI spec for the BILL v2 API was split into 10 files, covering 340+ endpoints across core BILL operations.

| Domain | Spec file coverage | Endpoints |
|---|---|---|
| Accounts Payable | Vendors, bills, recurring bills, payments, vendor credits | 88 |
| Accounts Receivable | Customers, invoices, recurring invoices, charge customers, credit memos | 65 |
| Organization Operations | Users, bank accounts, card accounts | 25 |
| Classifications | Chart of accounts, accounting class, location, department, payment terms | 144 |
| Authentication | Login, session, MFA | 5 |
| BILL Network Operations | Network search, vendor invites, large biller connections | 10 |

Even today, this structure mirrors how BILL customers actually use the API i.e. by business function, not alphabetically. Each OpenAPI spec file is uploaded to its own section in the ReadMe API reference. Developers working on AP payments simply find the section they need instead of having to navigate endpoints ordered by name.

In 2022, for each endpoint and related field description, I used Postman to test with real requests and responses in sandbox. I documented the role of each field, constraints, and specific behavior when the field name was not obvious.

:::note[BILL v2 API reference]
The BILL v2 API reference is published at [developer.bill.com/v2/reference/api-reference-overview](https://developer.bill.com/v2/reference/api-reference-overview).
:::

A publishing workflow that required manual uploads now ran in about a minute. This pipeline is maintained even today for every spec change, every API update, and every version release.

## Outcomes

#### 01 Forcing function

Publishing the complete v2 API reference had an unintended effect inside BILL. For the first time, BILL engineers, product managers, and leadership were looking at their own API through the same lens as external developers.

What they saw was uncomfortable: internal fields exposed in responses, misleading field names, non-standard error structures returning `HTTP 200` on failure. Issues API customers had been complaining about for years.

Teams moved to hide internal fields, improve error messages, and fix bugs that had been open for years. The docs weren't describing the API anymore. The docs were holding the API accountable.

#### 02 Input for v3

The most significant outcome of the v2 spec work wasn't the documentation itself.

The developer platform engineering team used the v2 spec files as the foundation for designing, building, and testing the BILL v3 API. They generated an internal SDK from the spec to validate the v3 experience before it was built.

:::note[From docs to engineering source]
A technical writer's output i.e. an OpenAPI spec written to document a public API became the engineering input for the next-generation product. Portable, tool-agnostic, and immediately useful across product, engineering, and release workflows.
:::
